That file is JSON. Each entry is a defect that two independent agents already established against
this code: `summary` and `evidence` state it, `verify_reason` is a second reader's confirmation

the surrounding code), `blast_radius` names what else the fix touches, and `test_plan` names the
test to write.

# How to work

1. Read `.claude/skills/{rust-gpui-testing,rust-workspace-architecture}/SKILL.md` and their `references/checklist.md`. They are this
   repo's engineering bar, distilled from the Zed codebase, and they are what your work is
   reviewed against. `docs/` is authoritative: if code and a doc disagree, one of them is a bug
   and both move together.
2. Take findings in severity order (high, then medium, then low).
3. For each finding: read the code around it and its existing tests. Satisfy yourself that the
   defect is real before you change anything. If you conclude it is not, leave the code alone and
   report `no_change_needed` with the reason — that is a correct and useful outcome.
4. **Write the regression test first, run it, and watch it fail for the stated reason.** Then make
   the fix and watch it pass. A test you never saw fail is not a regression test. If you cannot
   get it to fail first, say so plainly in your report instead of claiming you did.
5. Match the surrounding code exactly: its existing helpers, its adapter/fake seams, its
   test-module layout (inline `mod tests`, `src/<thing>/tests.rs`, or `crates/<crate>/tests/` —
   copy the neighbours), its comment density, its error-handling idiom.
6. Keep every fix minimal and surgical. No drive-by refactors, no renames, no reformatting of
   untouched code, no new features, no widening of a public API the fix does not need.
7. Verify with `cargo test -p <crate> <filter>` for the tests you added and
   `cargo check -p <crate> --all-targets`. Run them for real.

# Report back

End with a compact report: one line per finding id — `fixed` / `skipped` / `no_change_needed`,
what you changed with `file:line`, the test names you added, and the exact command you ran with
its real result. Then list every file you touched, and anything you deliberately left undone and
why.

Be accurate over optimistic. A skipped finding with a clear reason is worth far more than a
plausible claim that does not hold up — everything you report will be checked against the diff.
